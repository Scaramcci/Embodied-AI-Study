# EgoMimic 项目结构与运行逻辑（新手导读）

> 这份文档对应你当前下载的 EgoMimic 代码和 BowlPlace 样例数据，目标不是让你立刻背会每一行代码，而是先建立一张完整的“地图”：训练命令启动后，配置、数据、模型、损失、优化器、验证和 checkpoint 分别在哪里工作，又按照什么顺序连接起来。

## 1. 先用一句话理解这个项目

EgoMimic 是一个**离线模仿学习**项目：它不在训练时让机器人进入仿真器里试错，而是读取提前录制好的机器人示范和第一视角人类示范，训练一个视觉策略，使策略看到当前图像和当前状态后，一次预测未来一段动作（action chunk）。这个仓库主要覆盖三件事：

这个仓库主要覆盖三件事：

1. 把机器人或 Aria 眼镜采集的原始记录转换成统一的 HDF5 训练数据。
2. 用 ACT 或 EgoMimic 算法训练策略。
3. 离线验证预测误差并生成可视化视频；连接真实 ALOHA 机器人后的在线部署代码也在仓库中，但不属于当前纯训练复现的必要部分。

你当前要复现的是第 2、3 部分，数据已经下载并转换完成，所以暂时不用碰相机标定、SAM 分割或真实机器人控制代码。

## 2. 具身智能训练里的几个基本概念

在读代码前，先把项目中的术语对应起来：

| 名词                 | 在本项目中的含义                                                                     |
| -------------------- | ------------------------------------------------------------------------------------ |
| observation / `obs`  | 策略在当前时刻能看到的信息，例如前视图、腕部相机图像、机器人关节位置或人手三维位置   |
| action               | 专家在当前时刻之后应该执行的动作；这里不是只预测一步，而是预测未来 100 步            |
| demonstration / demo | 一段完整的专家操作轨迹，例如一次“把碗放到指定位置”                                   |
| policy               | 从 observation 映射到 action 的神经网络                                              |
| behavior cloning     | 把专家动作当标签，像监督学习一样训练策略模仿专家                                     |
| action chunk         | 一次性预测的一段未来动作序列；当前 medium 配置长度为 100                             |
| proprioception       | 本体状态，即机器人自身关节位置；人类数据中对应手部末端三维位置                       |
| offline validation   | 不操作机器人，只在留出的验证数据上比较预测动作与真实动作                             |
| rollout              | 真正把策略放进环境或机器人中连续执行。当前样例复现没有仿真环境，配置中已关闭 rollout |

最重要的输入输出关系可以记成：

```text
当前视觉图像 + 当前本体状态
              │
              ▼
       ACT / EgoMimic 策略
              │
              ▼
       未来 100 步动作序列
```

### 3.1 `external/robomimic` 为什么重要

EgoMimic 没有从零实现所有训练基础设施，而是在 robomimic 上扩展。你会看到很多这样的导入：

```python
import robomimic.utils.obs_utils as ObsUtils
from robomimic.utils.dataset import SequenceDataset
from robomimic.algo.bc import BC_VAE
```

robomimic 在本项目中主要负责：

- 从 HDF5 中按 demo 和时间索引取序列；
- 根据配置识别 RGB、low-dimensional observation 等模态；
- 图像从 `H×W×C` 转为 `C×H×W`、转浮点数并缩放；
- observation 和 action 的统计、归一化与反归一化；
- ResNet18 等视觉骨干；
- 优化器和学习率调度器的创建；
- `BC_VAE` 等算法基类。

可以把两者的关系理解为：

```text
robomimic：通用的模仿学习“地基”
EgoMimic：双域数据、ACT 策略、Lightning 训练和项目专用逻辑
```

初读时不需要深入 robomimic 全仓库。遇到 `SequenceDataset`、`ObsUtils`、`BC_VAE` 时，只要先知道它们提供什么服务即可。

## 4. 你当前数据的实际结构

HDF5 可以把它想象成“一个文件里的目录树”。两份样例数据的顶层结构是：

```text
bowlplace_*.hdf5
├── data/
│   ├── demo_0/
│   │   ├── obs/
│   │   │   ├── front_img_1
│   │   │   ├── front_img_1_line
│   │   │   ├── ...
│   │   ├── actions_joints_act
│   │   └── actions_xyz_act
│   ├── demo_1/
│   └── ...
└── mask/
    ├── train
    ├── valid
    ├── medium_train
    └── medium_valid
```

`mask` 不是图像 mask，而是**数据划分名单**：其中保存哪些 `demo_x` 属于训练集、哪些属于验证集。配置里的 `hdf5_filter_key` 就是从这里选名单。

### 4.1 Robot 数据

`bowlplace_robot.hdf5` 的一个 demo 包含：

| HDF5 key               | 单条 demo 的形状      | 含义                                              |
| ---------------------- | ---------------------:| ------------------------------------------------- |
| `obs/front_img_1`      | `(3000, 480, 640, 3)` | 普通前视相机图像                                  |
| `obs/front_img_1_line` | `(3000, 480, 640, 3)` | 加入轨迹/轮廓表达的前视图，EgoMimic medium 使用它 |
| `obs/right_wrist_img`  | `(3000, 480, 640, 3)` | 右腕相机图像                                      |
| `obs/joint_positions`  | `(3000, 7)`           | 当前 7 维机器人关节状态                           |
| `obs/ee_pose`          | `(3000, 3)`           | 当前末端位置的三维表示                            |
| `actions_joints_act`   | `(3000, 100, 7)`      | 每个时刻对应未来 100 步、每步 7 维的关节动作      |
| `actions_xyz_act`      | `(3000, 100, 3)`      | 同一未来轨迹的三维末端位置表达                    |

medium mask 使用 3 个 robot demo 训练、1 个 demo 验证，两者无重叠。

### 4.2 Human 数据

`bowlplace_human.hdf5` 的一个典型 demo 包含：

| HDF5 key               | 典型形状             | 含义                               |
| ---------------------- | --------------------:| ---------------------------------- |
| `obs/front_img_1_line` | `(300, 480, 640, 3)` | 人类第一视角图像，带统一的轨迹表达 |
| `obs/ee_pose`          | `(300, 3)`           | 当前手部末端位置                   |
| `actions_xyz_act`      | `(300, 100, 3)`      | 未来 100 步手部三维轨迹            |

medium mask 使用 42 个 human demo 训练、8 个 demo 验证，无重叠。

注意：Robot 和 Human 的关节结构不同，不能直接让人类数据监督“机器人七维关节动作”。EgoMimic 选择三维末端轨迹 `xyz` 作为二者都能表达的公共动作空间。

## 5. 配置系统如何工作

相关文件：

```text
egomimic/configs/
├── config.py                     # 支持 config.train.xxx 访问方式的嵌套字典
├── base_config.py                # 所有实验共有的默认配置
├── act_config.py                 # ACT 默认值以及 EgoMimic 在 ACT 上增加的默认值
├── act_medium.json               # 当前 ACT 小规模复现参数
└── egomimic_oboo_medium.json     # 当前 EgoMimic 小规模复现参数
```

程序不会直接把 JSON 当成任意字典使用。它先根据 JSON 中的：

```json
"algo_name": "egomimic"
```

调用 `config_factory("egomimic")`，创建 `EgoMimicConfig` 的完整默认配置；然后再用 JSON 覆盖默认值。这样既能补齐没写出的默认参数，也能在 JSON 写错 key 时尽早报错。最后 `config.lock()` 会锁住配置，避免训练途中意外增加或修改字段。

### 5.1 JSON 的四个核心区域

#### `experiment`

控制一次实验怎么运行和保存：

- `name`、`description`：决定输出目录层级；
- `validate`：是否做离线验证；
- `epoch_every_n_steps`：一个“人为定义的 epoch”包含多少个梯度 step；
- `validation_freq`：每多少个 epoch 做一次验证；
- `validation_max_samples`：一次验证最多处理多少样本；
- `save.every_n_epochs`：checkpoint 保存频率；
- `save.video_freq`：验证视频频率；
- `rollout.enabled`：是否进入环境执行，本次为 `false`。

这里的 epoch 不一定等于“完整遍历一遍数据集”。medium 配置明确限制为每 epoch 100 个 batch，因此：

```text
500 epochs × 100 training steps/epoch = 50,000 optimizer steps
```

#### `train`

控制数据和训练规模：

- `data` / `data_2`：机器人、人类 HDF5 路径；
- `data_type` / `data_2_type`：把样本标记为 `robot` 或 `hand`；
- `hdf5_filter_key`：机器人训练 mask；
- `hdf5_2_filter_key`：人类训练 mask；
- `hdf5_validation_filter_key`：验证 mask；
- `dataset_keys`：要从 HDF5 读取的动作字段；
- `ac_key` / `ac_key_hand`：当前模态的主动作字段；
- `seq_length`：动作 chunk 长度；
- `prestacked_actions: true`：HDF5 已经为每个时刻预存好了未来动作序列；
- `batch_size`、`num_epochs`、`num_data_workers`：训练大小和加载并发；
- `hdf5_cache_mode: low_dim`：只把小体积数值数据缓存到内存，图像按需读取；
- `hdf5_normalize_obs/actions`：是否用训练集统计量归一化。

#### `algo`

控制网络和损失：

- AdamW 与学习率；
- Transformer hidden dimension、层数、head 数；
- VAE latent dimension；
- `kl_weight`：KL loss 权重；
- EgoMimic 的 `hand_lambda`：人类数据 loss 权重。

#### `observation` 与 `observation_hand`

声明每种数据真正送进网络的 observation key，并告诉 robomimic 哪些是 RGB，哪些是低维状态。

例如当前 EgoMimic medium 配置：

```text
Robot: front_img_1_line + right_wrist_img + joint_positions
Human: front_img_1_line + ee_pose
```

HDF5 里即使还有其他字段，只要没有写进 observation 配置，就不会成为策略输入。

## 6. ACT 模型到底做了什么

ACT 是 Action Chunking with Transformers。当前实现位于：

- `egomimic/algo/act.py`：把 batch 转成 ACT 输入、前向传播、loss 和推理；
- `egomimic/models/act_nets.py`：Transformer 与 StyleEncoder；
- robomimic 的视觉 backbone：每个相机对应一个 ResNet18。

### 6.1 训练时的网络路径

```text
各相机当前图像 ──> 各自的 ResNet18 ──> 拼接视觉 token ─────────────┐
当前关节位置 ──────────────────────> proprio token ───────────────┤
真实未来动作 + 当前关节 ──> StyleEncoder ──> latent z ────────────┤
                                                                  ▼
                                                         Transformer
                                                                  │
                                            100 个 learnable query │
                                                                  ▼
                                                    未来 100 步动作
```

训练时 StyleEncoder 看到了真实未来动作，用它得到高斯分布的 `mu`、`logvar` 并采样 latent `z`。这是条件 VAE 的部分。推理时未来动作当然未知，所以代码把 latent 设为全零，再根据当前 observation 预测动作。

### 6.2 ACT loss

ACT 的主要 loss 是：

```text
action_loss = L1(predicted_actions, expert_actions)
              + kl_weight × KL(q(z|state, actions) || N(0, I))
```

序列末尾不足 100 步时数据集会 padding，`pad_mask` 会阻止这些补齐位置进入有效的 L1 loss。

### 6.3 为什么一次预测 100 步

逐帧预测一个动作容易抖动，也难以表达一段连贯技能。ACT 将一段未来动作作为一个整体预测，让 Transformer 学到动作之间的时间结构。真实部署代码不会盲目一次执行完 100 步，而是按一定 `query_frequency` 重新查询策略；还可以对多次预测的重叠部分做 temporal aggregation。

## 7. EgoMimic 相比 ACT 增加了什么

ACT baseline 只训练 Robot 数据：

```text
Robot 图像 + joint_positions → 未来 actions_joints_act
```

EgoMimic 同时训练 Robot 和 Human 两种数据：

```text
Robot batch:
  front + wrist + joint_positions
       → robot joint head → actions_joints_act
       → shared xyz head  → actions_xyz_act

Human batch:
  front + ee_pose
       → shared xyz head  → actions_xyz_act
```

核心设计在 `egomimic/algo/egomimic.py`：

- 共享 Transformer 和主要视觉表示；
- Robot 使用机器人状态投影和七维 joint action head；
- Human 使用手部状态投影和三维 action head；
- Robot 数据同时监督 joint head 和三维 hand/xyz head；
- Human 数据监督同一个三维 hand/xyz head；
- 这使第一视角人类视频能够通过公共的三维轨迹表达，帮助机器人策略学习视觉与动作之间的关系。

在 `ModelWrapper.training_step()` 中，EgoMimic 每个训练 step 收到一个 Robot batch 和一个 Human batch，分别计算 loss，最后对两个 loss 字典取平均，再由 Lightning 做反向传播。因此这里的 `batch_size: 4` 可以理解为每个数据加载器各取 4 条样本，而不是两种数据合计只有 4 条。

ACT 只有一个数据加载器，因此每步只有 Robot batch。

## 8. 从命令到参数更新：完整运行顺序

下面是最值得反复对照源码的一节。

### 阶段 A：启动和解析配置

入口是：

```bash
python scripts/pl_train.py --config configs/egomimic_oboo_medium.json --no-wandb
```

执行顺序：

1. Python import `egomimic`、config 和 algo 模块。
2. `configs/__init__.py` 导入配置类，使 `ACTConfig`、`EgoMimicConfig` 注册到 config factory。
3. `algo/__init__.py` 导入算法类，使 `act`、`egomimic` 注册到 algo factory。
4. `train_argparse()` 解析命令行参数。
5. 非 eval 模式下，脚本给 `description` 加上日期时间，避免覆盖上一次实验。
6. `main(args)` 读取 JSON，根据 `algo_name` 创建默认配置，再用 JSON 覆盖。
7. 命令行中的 `--dataset`、`--batch-size` 等参数如果存在，会再次覆盖 JSON。
8. `--debug` 会进一步把 epoch、step、验证样本数和 worker 改小；因此 debug 运行不是正式 medium 规模。
9. 检查验证频率、保存频率和视频频率之间的约束，然后锁定配置。
10. 调用 `pl_train_utils.train(config, ckpt_path)`。

覆盖优先级是：

```text
Python 默认配置 < JSON 配置 < 命令行参数 < debug 模式强制修改
```

### 阶段 B：创建实验目录

`utils/train_utils.py:get_exp_dir()` 创建：

```text
trained_models_highlevel/
└── <experiment.name>/
    └── <experiment.description_时间>/
        ├── config.json
        ├── ds1_norm_stats.pkl
        ├── ds2_norm_stats.pkl       # EgoMimic 才有
        ├── logs/
        ├── models/
        └── videos/
```

`config.json` 是**所有覆盖完成后的最终配置**，复盘实验时应以它为准，而不是只看原始配置文件。

### 阶段 C：初始化 observation 和数据集

`pl_train_utils.train()` 依次完成：

1. 设置随机种子和 GPU 数值计算选项。
2. `ObsUtils.initialize_obs_utils_with_config(config)`：登记哪些 key 是 RGB、low_dim 等模态。
3. 检查 HDF5 路径是否存在。
4. `get_shape_metadata_from_dataset()`：读取 observation shape 和 action dimension。
5. `load_data_for_training()`：读取 `medium_train` / `medium_valid` 中的 demo 名单，并强制检查 train/valid 不重叠。
6. `dataset_factory()` 创建 `PlaydataSequenceDataset`。
7. 计算训练集 normalization stats，并保存成 pkl。
8. EgoMimic 会复制一份 config，换成人类 observation、action key 和 mask，再创建第二组数据集。

`PlaydataSequenceDataset.get_item(index)` 真正取样时会：

1. 把全局 index 映射到某个 `demo_x` 和 demo 内时间位置；
2. 取出配置要求的动作序列；
3. 只给 RGB 取当前帧，而不是读取未来 100 张大图；
4. 取出 low-dimensional sequence 和 `pad_mask`；
5. Robot 样本加 `type=0`，Human 样本加 `type=1`。

### 阶段 D：构造 DataLoader

`pl_utils/pl_data_utils.py` 把 Dataset 包装成 LightningDataModule：

- ACT → `DataModuleWrapper` → 一个 Robot DataLoader；
- EgoMimic → `DualDataModuleWrapper` → Robot、Human 两个 DataLoader；
- `batch_size=4`、`num_workers=2`、`pin_memory=True`；
- 训练集 shuffle，验证集不 shuffle；
- `drop_last=True` 保证 batch 大小固定。

### 阶段 E：根据数据自动创建模型

`ModelWrapper(config.dump(), shape_meta, datamodule)` 初始化时：

1. 根据 `algo_name` 调用 `algo_factory()`。
2. `act` 创建 `ACT`；`egomimic` 创建 `EgoMimic`。
3. 算法从 `shape_meta` 得知 action dimension 和各 observation shape。
4. `_create_networks()` 创建 ResNet、StyleEncoder、Transformer 和 action head。
5. 算法基类读取 `optim_params`，创建 AdamW 与 scheduler。
6. `ModelWrapper` 把这些普通 robomimic 模型包装成 LightningModule，使 Lightning 能接管 GPU、反向传播、DDP 和 checkpoint。

### 阶段 F：一个训练 step 内发生什么

Lightning 调用 `ModelWrapper.training_step(batch, batch_idx)`：

```text
HDF5 sample
  ↓ DataLoader 合并成 batch
  ↓ process_batch_for_training：筛选 key、取当前图像/状态、搬到 GPU
  ↓ postprocess_batch_for_training：图像转 BCHW/float，obs 与 action 归一化
  ↓ _forward_training：ResNet + StyleEncoder + Transformer + action head
  ↓ _compute_losses：L1 reconstruction + KL
  ↓ training_step 返回 action_loss
  ↓ Lightning 自动执行 backward()
  ↓ AdamW optimizer.step()
  ↓ scheduler.step(global_step)
```

EgoMimic 会对 Robot、Human 两个 batch 各走一次中间流程，然后平均 loss。ACT 只走一次。

一个常见误区是以为 `training_step()` 中应该手写 `loss.backward()`。这里不能再手写，因为 Lightning 的 automatic optimization 已经负责 backward、optimizer step 和梯度清零。

### 阶段 G：epoch、验证和保存

Lightning 最多运行 `num_epochs=500`，每个 epoch 由 `limit_train_batches=100` 限制为 100 个训练 step。

本项目的离线验证不是标准 `validation_step()`，而是在 `ModelWrapper.on_train_epoch_start()` 中手动触发：

1. 到达 `validation_freq` 的倍数 epoch；
2. 只在 rank 0 上执行；
3. `evaluate_high_level_policy()` 遍历验证 DataLoader；
4. 用 `forward_eval()` 预测动作；
5. 反归一化预测；
6. 计算 paired MSE 和 final MSE；
7. 把真实轨迹与预测轨迹画到图像上；
8. 写入 `videos/robot_*.mp4` 和 EgoMimic 的 `videos/hand_*.mp4`。

颜色大意是：真实轨迹和预测轨迹使用不同色系；EgoMimic 的 Robot 验证还会显示辅助 xyz head 的轨迹。

`ModelCheckpoint` 在每 `save.every_n_epochs` 个 epoch 后保存：

```text
models/model_epoch_epoch=<N>.ckpt
models/last.ckpt
```

checkpoint 不只是网络权重，还含 Lightning 状态、optimizer、scheduler 和保存过的 config，因此可以继续训练或离线评估。

## 10. 两条实验路径怎么理解

建议先跑 ACT，再跑 EgoMimic。不是因为 ACT 是最终目标，而是它更适合用来定位问题。

| 对比项        | ACT medium         | EgoMimic medium                      |
| ------------- | ------------------ | ------------------------------------ |
| 数据          | Robot              | Robot + Human                        |
| DataLoader 数 | 1                  | 2                                    |
| 主要输出      | Robot joint action | Robot joint action + 公共 xyz action |
| 验证          | Robot              | Robot + Human                        |
| 目的          | 基础对照组         | 验证人类第一视角数据是否带来帮助     |
| 调试难度      | 较低               | 较高                                 |

如果 ACT 能运行而 EgoMimic 不能，通常应优先检查 Human HDF5、`observation_hand`、`ac_key_hand`、第二个 normalization stats 或双 DataLoader，而不是 CUDA 和 ResNet。

## 11. 你接下来阅读代码的推荐顺序

不要从 `algo/egomimic.py` 第一行硬啃到底。推荐分五轮阅读：

### 第一轮：只建立地图

1. 打开 `configs/egomimic_oboo_medium.json`。
2. 对照本文件第 5 节，找出 Robot/Human 的图像、状态、动作 key。
3. 打开 `scripts/pl_train.py`，只读 `main()`。
4. 打开 `pl_utils/pl_train_utils.py`，只读 `train()`。

目标：能口述“配置在哪里读、数据在哪里创建、模型在哪里创建、Trainer 从哪里启动”。

### 第二轮：跟踪一条数据

依次读：

```text
dataset_factory()
  → PlaydataSequenceDataset.get_item()
  → DataModuleWrapper / DualDataModuleWrapper
  → ModelWrapper.training_step()
  → process_batch_for_training()
```

目标：知道 HDF5 中一个时间点如何成为 GPU 上的 batch。

### 第三轮：跟踪一次前向传播

依次读：

```text
ACT._forward_training()
  → ACT._robomimic_to_act_data()
  → ACTModel.forward()
  → ACTModel._forward()
  → Transformer.forward()
  → ACT._compute_losses()
```

目标：在纸上写出主要 tensor 的形状，例如：

```text
qpos:       [B, 7]
images:     [B, 2, 3, H, W]
actions:    [B, 100, 7]
prediction: [B, 100, 7]
```

### 第四轮：理解 EgoMimic

先理解 ACT，再只比较 `algo/egomimic.py` 覆盖了 ACT 的哪些方法：

- `build_model_opt()`；
- `_create_networks()`；
- `process_batch_for_training()`；
- `_robomimic_to_act_data()`；
- `_forward_training()`；
- `forward_eval()`。

目标：能解释哪些参数共享、哪些 head 是模态专用、Human 数据如何参与 loss。

### 第五轮：理解验证与部署边界

阅读 `utils/val_utils.py`，再浏览 `scripts/evaluation/eval_real.py`。不要把两者混为一谈：

- 前者只对已有数据做预测误差评估，不会控制机器人；
- 后者会读取相机和关节、查询模型并向真实机器人发送动作。

## 12. 第一次自己运行时应该观察什么

这不是让你机械复制命令，而是给你一张观察清单。执行 debug 或正式训练时，应确认日志按顺序出现：

1. 打印最终 config；
2. 打印 Robot observation/action shape；
3. 打印 `Training Dataset` 和 normalization stats；
4. EgoMimic 再打印 Human dataset 和第二份 stats；
5. 打印模型 summary 与参数量；
6. GPU 被 Lightning 识别；
7. 进度条中的 loss 能持续产生有限数值，而不是 `nan`；
8. 到验证 epoch 后生成 mp4；
9. 到保存 epoch 后生成 ckpt；
10. 最终出现 `finished run successfully!`。

看到问题时，按所属阶段定位：

| 现象                    | 首先检查                                         |
| ----------------------- | ------------------------------------------------ |
| 配置 key 不存在         | `configs/*.json` 与 `act_config.py`              |
| Dataset not found       | 当前工作目录以及 `train.data` 相对路径           |
| HDF5 key 不存在         | observation、dataset_keys、ac_key 是否与数据一致 |
| train/valid overlap     | HDF5 的 `mask`                                   |
| DataLoader worker 崩溃  | 先把 `num_data_workers` 改为 0 看真实异常        |
| CUDA OOM                | batch size、图像数量、是否还有其他 GPU 进程      |
| loss 是 nan             | normalization stats、输入异常值、学习率          |
| 训练正常但验证视频失败  | PyAV/torchvision 兼容性与写入目录                |
| ACT 正常、EgoMimic 失败 | Human 数据字段和双 DataLoader 路径               |

## 13. 当前复现范围的边界

完成 medium 训练并不等于完成论文中的全部真实机器人复现。可以把复现分为三个层级：

1. **代码复现**：debug 跑通，确认数据、前向、loss、反向和保存都工作。
2. **离线实验复现**：正式训练 ACT 与 EgoMimic，比较验证误差和视频质量。
3. **真实机器人复现**：准备 ALOHA/Eve、相机标定、安全控制、现场物体和成功率评估。

你当前正从第 1 层进入第 2 层。4090 Laptop 足以完成这个 medium 版本；真正需要租服务器的情况通常是扩大数据量、同时做多组随机种子/超参数对比，或者追求论文级多任务实验，而不是因为当前代码必须依赖服务器。`pl_submit.py` 是作者集群环境专用入口，单机复现应继续使用 `pl_train.py`。
