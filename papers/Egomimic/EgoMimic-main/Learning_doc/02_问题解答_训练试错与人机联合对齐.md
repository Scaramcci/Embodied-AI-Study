# 问题解答：训练中的“试错”、robomimic，以及 EgoMimic 的人机联合训练

> 本文回答三个互相关联的问题：
>
> 1. “训练时不让机器人进入仿真器试错”到底是什么意思？
> 2. `external/robomimic` 目录里的各部分有什么作用？
> 3. EgoMimic 如何把 Human 和 Robot 数据对齐并联合训练？两边字段和维度不一致时怎么办？
>
> 本文依据你当前 checkout 的源码、当前 BowlPlace HDF5 样例数据，以及 EgoMimic 论文正文与附录编写。代码路径均相对于 `EgoMimic-main/`。

## 问题一：训练时“不进入仿真器试错”是什么意思？

### 1. 不是所有机器人训练都会进入仿真器

“正常训练会进仿真器试错吗？”这个问题没有统一的“会”或“不会”，因为机器人学习至少有几种不同范式：

| 学习范式                        | 训练数据从哪里来             | 训练时是否与环境交互 | 常见的“试错”                                             |
| ------------------------------- | ---------------------------- | -------------------- | -------------------------------------------------------- |
| 强化学习（RL）                  | 策略与仿真或真实环境交互产生 | 是                   | 策略执行动作，得到新状态和奖励，根据成功/失败更新        |
| 在线模仿学习（如 DAgger）       | 策略运行时由专家继续纠正     | 是                   | 策略犯错后收集纠正标签，再加入训练集                     |
| 离线模仿学习 / Behavior Cloning | 预先收集且固定的专家数据集   | 否                   | 本质是监督学习，比较预测动作与专家动作，没有环境反馈     |
| 离线强化学习                    | 预先收集且固定的交互数据集   | 否                   | 用固定数据中的 reward 学价值或策略，不在训练中产生新交互 |

EgoMimic 当前这条训练路径属于第三种：**离线模仿学习**。

因此，更准确的说法不是“正常机器人训练应该进入仿真器”，而是：

- 有些方法，尤其在线强化学习，会把仿真器作为训练环境；
- EgoMimic 的训练代码把已经录制好的示范当成固定数据集，不需要仿真器；
- 仿真环境也可以只用于训练后的 rollout 验证，但这是另一种用法。

### 2. “试错”在强化学习里具体是什么

假设任务是“把碗放到盒子里”。一次强化学习交互可以写成：

```text
当前 observation s_t
        │
        ▼
策略选择 action a_t
        │
        ▼
环境/仿真器执行动作
        │
        ├──> 新 observation s_{t+1}
        ├──> reward r_t
        └──> episode 是否结束
```

“试错”指策略为了学习，反复进行这种交互：

- 手伸错方向、没抓住碗，奖励低；
- 撞到桌子或把碗碰倒，奖励低或受到惩罚；
- 成功抓起并放进盒子，获得较高奖励；
- 算法利用这些结果提高未来选中好动作的概率。

这里的“错”不是程序抛异常，而是**动作在任务意义上效果不好**。强化学习依赖环境反馈来判断动作的长期结果，所以训练时必须有可交互的环境；环境可以是真实机器人，也可以是仿真器。真实机器人试错成本高、速度慢且有安全风险，因此很多强化学习工作会先在仿真器训练。

### 3. 仿真器既可以训练，也可以验证

你说“进仿真不应该是训练完后部署在仿真里验证吗？”——这确实是一种常见流程，但不是仿真器唯一的用途。

同一个仿真平台可以承担两种角色：

```text
训练环境：产生大量交互，用于更新模型参数
测试环境：冻结模型参数，在未见过的场景/随机种子中衡量成功率
```

必须区分的不是“是不是同一个仿真软件”，而是：

- 这段环境交互有没有用于更新参数？如果有，它属于训练；
- 模型是否已经冻结，只记录成功率？如果是，它属于验证或测试。

例如，强化学习可以在仿真器的 10,000 个随机场景上训练，再在另外 1,000 个未参与更新的随机场景上测试。模仿学习也可以先用固定示范训练，再把模型放进仿真器 rollout，检查它闭环执行时能否完成任务。

### 4. EgoMimic 训练中实际发生的“误差”不是环境试错

EgoMimic 的一次训练样本大致是：

```text
输入：当前相机图像 + 当前关节/手部位置
标签：专家接下来 100 步动作
预测：模型预测的接下来 100 步动作
loss：预测动作和专家动作之间的 L1 误差 + VAE KL loss
```

模型会产生预测误差，并通过反向传播减小误差，但它没有真的让机器人执行这段预测，也没有从环境中看到“碗是否被抓起来”。因此这里是**监督误差**，不属于强化学习语境里的环境试错。

可以类比：

- 离线模仿学习像看带答案的练习册，写出答案后和标准答案比较；
- 强化学习像进入实验室自己操作，通过实验是否成功来学习；
- rollout 测试像考试，模型参数不再修改，只看实际完成任务的能力。

### 5. EgoMimic 当前有哪种验证

你现在的 `egomimic_oboo_medium.json` 中：

```json
"validate": true,
"rollout": {
    "enabled": false
}
```

所以当前流程是：

```text
固定 HDF5 train split
        │
        ▼
训练模型
        │
        ▼
固定 HDF5 valid split 上计算动作 MSE、生成视频
```

这叫**离线验证**。它能回答“模型对留出的专家数据预测得准不准”，但不能完整回答“模型真实闭环执行会不会成功”。原因是闭环部署存在 distribution shift：某一步预测稍有偏差后，下一步看到的状态可能已经偏离训练数据，而离线验证不会模拟这种误差积累。

仓库中的 [`egomimic/scripts/evaluation/eval_real.py`](../egomimic/scripts/evaluation/eval_real.py) 才是读取真实相机、读取真实关节并控制 ALOHA 的在线 rollout 路径。它需要 Eve/ALOHA 硬件环境，不属于你当前这一步。

### 6. 对第一个问题的直接结论

1. “机器人训练”不是一种单一流程；强化学习常在仿真中边交互边训练，离线模仿学习则不需要。
2. “试错”是执行动作后根据环境结果或 reward 学习，不是普通的训练 loss，也不是代码报错。
3. 仿真器既能当训练环境，也能在模型冻结后当测试环境。
4. EgoMimic 当前使用固定人类/机器人示范做监督训练，训练期间不进入仿真器。
5. 当前代码做的是离线动作预测验证；最终任务成功率仍需真实机器人 rollout，或者另行构建与数据、机器人相匹配的仿真环境。

## 问题二：robomimic 目录中每一部分做什么？

### 1. robomimic 在这里扮演什么角色

robomimic 是一个“从机器人示范中学习”的通用框架。原版提供标准 HDF5 数据接口、行为克隆和离线强化学习算法、视觉编码器、环境封装、训练与评估工具。

EgoMimic 没有直接使用 robomimic 自带的整个训练入口，而是：

- 复用 robomimic 的 Dataset、observation 处理、归一化、视觉 backbone、算法基类和优化器工具；
- 自己增加 ACT/EgoMimic 算法；
- 自己用 PyTorch Lightning 组织训练循环；
- 自己增加 Human/Robot 双数据加载和跨具身逻辑。

### 2. 根目录

```text
external/robomimic/
├── robomimic/          # 真正的 Python 包
├── docs/               # Sphinx 文档源码、教程、数据和模型说明
├── examples/           # Notebook 与简单使用示例
├── tests/              # 自动化测试
├── README.md           # 项目介绍与文档入口
├── requirements.txt    # Python 依赖
├── setup.py            # pip install -e 时使用的安装配置
├── MANIFEST.in         # Python 包发布时额外包含哪些文件
└── LICENSE             # 许可证
```

其中训练时真正被 import 的是 `external/robomimic/robomimic/`。

### 3. `robomimic/algo/`：算法层

```text
algo/
├── algo.py       # 所有算法的基类、注册工厂、optimizer 创建等
├── bc.py         # Behavior Cloning、BC-RNN、BC-VAE 等
├── bcq.py        # Batch-Constrained Q-learning
├── cql.py        # Conservative Q-Learning
├── iql.py        # Implicit Q-Learning
├── td3_bc.py     # TD3 + Behavior Cloning
├── hbc.py        # Hierarchical Behavior Cloning
├── gl.py         # Goal learning 相关算法
└── iris.py       # 分层离线 RL 算法
```

EgoMimic 当前最直接依赖的是：

- `algo/algo.py` 中的通用算法接口和 optimizer/scheduler 创建；
- `algo/bc.py` 中的 `BC_VAE`，ACT 和 EgoMimic 继承它的 VAE/BC 基础能力。

BC 是监督模仿学习；BCQ、CQL、IQL、TD3-BC 是离线强化学习算法，当前 EgoMimic medium 不会执行它们。

### 4. `robomimic/config/`：配置层

```text
config/
├── config.py              # 可锁定、可用属性访问的嵌套配置字典
├── base_config.py         # 公共默认字段
├── bc_config.py           # BC 的默认配置
├── bcq_config.py          # BCQ 配置
├── cql_config.py          # CQL 配置
├── iql_config.py          # IQL 配置
├── ...
└── default_templates/     # 自动生成的默认 JSON 模板
```

EgoMimic 仓库复制并扩展了这种 config/factory 思路，在自己的 [`egomimic/configs/`](../egomimic/configs/) 中维护 ACT 和 EgoMimic 配置。因此你正式实验时主要修改 EgoMimic 自己的 JSON，不要去改 robomimic 的 `bc_config.py`。

### 5. `robomimic/envs/`：环境适配层

```text
envs/
├── env_base.py        # 环境统一接口
├── env_robosuite.py   # robosuite/MuJoCo 环境适配
├── env_gym.py         # Gym 环境适配
├── env_ig_momart.py   # iGibson/MOMART 相关适配
└── wrappers.py        # 环境 wrapper
```

这部分主要服务于 simulator rollout：reset 环境、执行 action、获取 observation、判断 success。

你当前训练的 `rollout.enabled=false`，而且 BowlPlace 样例 HDF5 的 `env_args` 为空，所以 medium 离线训练不会由这些文件创建仿真器。这也从代码层面印证了问题一的结论。

### 6. `robomimic/models/`：通用网络组件

```text
models/
├── base_nets.py       # MLP、ResNet18Conv、SpatialSoftmax 等基础网络
├── obs_core.py        # 单种 observation 的编码核心
├── obs_nets.py        # 多模态 observation encoder/decoder
├── policy_nets.py     # 通用 actor、RNN、GMM policy
├── transformers.py    # 位置编码和 Transformer 工具
├── vae_nets.py        # 通用 VAE 组件
├── value_nets.py      # value/Q 网络
├── distributions.py   # 概率分布封装
└── vit_rein.py        # ViT 视觉表示相关代码
```

当前 ACT/EgoMimic 主要使用：

- `base_nets.ResNet18Conv` 编码相机图像；
- `transformers.PositionalEncoding` 给动作和视觉 token 加位置编码。

EgoMimic 自己的 [`models/act_nets.py`](../egomimic/models/act_nets.py) 再实现专用的 Transformer 和 StyleEncoder。

### 7. `robomimic/utils/`：基础设施工具

这是当前复现中使用最多的 robomimic 目录。

| 文件                  | 作用                                              | EgoMimic 中的实际例子                                              |
| --------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| `dataset.py`          | HDF5 demo 索引、序列采样、padding、缓存、统计量   | `PlaydataSequenceDataset` 继承 `SequenceDataset`                   |
| `obs_utils.py`        | 识别 RGB/low_dim 模态、图像换轴缩放、归一化       | batch 图像从 NHWC 处理成网络需要的 NCHW                            |
| `file_utils.py`       | 读取 HDF5 metadata、mask、shape，加载 checkpoint  | 根据 `medium_train` 找 demo，根据 action key 得到 action dimension |
| `tensor_utils.py`     | 嵌套字典里的 tensor 搬 GPU、转 float、detach      | `process_batch_for_training()` 使用                                |
| `torch_utils.py`      | 根据配置创建 optimizer、scheduler、计算梯度等     | 创建 AdamW 和 linear scheduler                                     |
| `train_utils.py`      | robomimic 原版训练、dataset factory、rollout 工具 | EgoMimic 自己也有同名扩展文件，不要混淆                            |
| `env_utils.py`        | 从 metadata 创建环境                              | 当前离线训练不用                                                   |
| `log_utils.py`        | 日志、终端输出、DataLogger                        | 部分工具和 baseline 会使用                                         |
| `loss_utils.py`       | 常用 loss 辅助函数                                | 其他算法使用较多                                                   |
| `vis_utils.py`        | 图像可视化                                        | 调试工具使用                                                       |
| `python_utils.py`     | Python 通用辅助类                                 | 配置和后台处理等                                                   |
| `hyperparam_utils.py` | 超参数 sweep                                      | 当前 medium 不用                                                   |

特别注意有两套同名文件：

```text

egomimic/utils/train_utils.py                      # EgoMimic 项目扩展版
```

看 import 的完整路径才能知道实际调用哪一个。

### 8. `robomimic/scripts/`：可执行工具

```text
scripts/
├── train.py                    # robomimic 原版训练入口
├── run_trained_agent.py        # 加载模型并 rollout
├── playback_dataset.py         # 回放数据集
├── get_dataset_info.py         # 查看 HDF5 信息
├── split_train_val.py          # 生成 train/valid mask
├── download_datasets.py        # 下载官方数据
├── dataset_states_to_obs.py    # 从状态重新生成 observation
├── generate_config_templates.py
├── generate_paper_configs.py
├── hyperparam_helper.py
```

EgoMimic 不从 `robomimic/scripts/train.py` 启动，而是从 [`egomimic/scripts/pl_train.py`](../egomimic/scripts/pl_train.py) 启动。数据转换时会复用 `split_train_val.py` 生成 HDF5 的 `mask/train` 和 `mask/valid`。

### 9. `robomimic/exps/` 和 `macros*.py`

- `exps/` 保存 robomimic 官方实验模板和预设，不是训练输出目录。
- `macros.py` 放机器相关的全局设置。
- `macros_private.py` 由 `setup_macros.py` 生成，可放 W&B 用户名等本机私有配置；不应提交敏感信息。

### 10. 你阅读 robomimic 的最小路线

不用通读所有离线 RL 算法。为了理解 EgoMimic，只需按顺序看：

```text

    ↓
robomimic/utils/file_utils.py
    ↓
robomimic/algo/algo.py
    ↓
robomimic/algo/bc.py 中的 BC_VAE
    ↓
robomimic/models/base_nets.py 中的 ResNet18Conv
```

## 问题三：EgoMimic 如何对齐 Human 与 Robot 数据并联合训练？

### 1. 最重要的澄清：这里不是一一配对对齐

“对齐”很容易让人以为数据必须是这样：

```text
human demo 第 135 帧  <──精确对应──>  robot demo 第 287 帧
```

当前 EgoMimic **不要求 Human 和 Robot demo 成对，也没有用动态时间规整或人工标签把两个 demo 的每一帧对应起来**。Human 可以在不同时间、不同场景独立采集。

EgoMimic 做的是让两种数据满足“可以进入一个共享策略”的条件：

```text
硬件/视角对齐
    + 坐标系对齐
    + 时间表示对齐
    + 数值分布对齐
    + 外观对齐
    + 共享网络与公共动作空间
```

所以这是**表示层面的跨具身对齐**，不是样本一一配对。

### 2. 两种原始数据本来有什么不同

根据论文和当前代码，两边原始信息是：

| 项目         | Human / Aria                | Robot / ALOHA                                  |
| ------------ | --------------------------- | ---------------------------------------------- |
| 主视觉       | 人佩戴 Aria 的第一视角 RGB  | 安装在机器人“头部”位置的 Aria/高位第一视角 RGB |
| 额外视觉     | 没有腕部相机                | 左/右 wrist camera                             |
| 当前自身状态 | Aria MPS 得到的手掌三维位置 | 机器人关节位置和通过 FK 得到的末端位置         |
| 可用动作     | 未来手掌三维轨迹            | 未来关节动作和未来末端三维轨迹                 |
| 单臂维度     | pose/action 都是 3 维 xyz   | joint 是 7 维，EEF xyz 是 3 维                 |
| 典型采样率   | 30 Hz                       | 50 Hz                                          |
| 外观         | 人手和手臂                  | 机械臂和夹爪                                   |
| 执行速度     | 人通常更快                  | 遥操作机器人通常更慢                           |

直接把这些数据混在一起会遇到至少五类 gap。

### 3. Gap 一：相机视角和传感器成像不同

#### 问题

如果 Human 是头戴第一视角，而 Robot 是远处固定第三视角，即使做同一任务，像素分布也完全不同。网络很容易先学会“这是人还是机器人”，而不是学习物体、动作和任务阶段。

不同相机的 FOV、动态范围、颜色、安装高度也会造成 camera domain gap。

#### EgoMimic 的处理

论文中的硬件设计直接在 Robot 主视角使用第二副 Aria，并安装在类似人眼/躯干顶部的位置，从数据采集源头缩小相机差异。

在你当前配置和数据中，公共视觉 key 是：

```text
Human: obs/front_img_1_line  (480, 640, 3)
Robot: obs/front_img_1_line  (480, 640, 3)
```

两边使用相同 key、相同分辨率，进入 Robot 的第一个视觉 backbone。Robot 独有的：

```text
obs/right_wrist_img
```

不会为了凑齐 Human 输入而伪造或补零。代码在 [`egomimic/algo/egomimic.py`](../egomimic/algo/egomimic.py) 中让：

- Robot 使用 `self.camera_keys`，即 front + wrist；
- Human 使用 `self.camera_keys[:1]`，即只使用公共 front；
- front 对应的 ResNet backbone 被两种数据共同更新；
- wrist backbone 只在 Robot batch 中得到梯度。

这是一种很实用的“不对称输入”处理：共享能共享的输入，保留 Robot 独有的有用传感器，而不是要求所有 embodiment 拥有完全相同的 observation。

### 4. Gap 二：Human 和 Robot 的坐标系不同

#### 问题

Human 手部位置最初属于 Aria device/SLAM 相关坐标；Robot 的关节角属于各关节坐标，FK 后的末端位置属于 robot base 坐标。如果直接混用：

```text
[0.1, 0.2, 0.5]（Human camera frame）
[0.1, 0.2, 0.5]（Robot base frame）
```

数值相同也不代表空间中的相同方向和位置。

#### Human 侧处理

源码位于 [`egomimic/scripts/aria_process/aria_to_robomimic.py`](../egomimic/scripts/aria_process/aria_to_robomimic.py)。对于时刻 `t`：

1. 从 Aria MPS 取得当前 palm position；
2. 利用设备与 RGB camera 的变换处理当前手部位置；
3. 对未来 `t + offset` 的手部位置，先利用对应时刻 camera pose 转到 world frame；
4. 再使用当前时刻 `t` 的 camera pose 逆矩阵，把未来手部点表达在**当前 camera-t frame**；
5. 对轴方向做旋转/符号变换，统一项目坐标约定；
6. 无效、越出图像或跳变异常的轨迹被过滤。

因此 Human action 不是“全局世界坐标里的一串绝对点”，而是站在当前观察图像对应相机坐标系中描述的未来手部轨迹。

#### Robot 侧处理

源码位于 [`egomimic/scripts/aloha_process/aloha_to_robomimic.py`](../egomimic/scripts/aloha_process/aloha_to_robomimic.py)：

1. 读取 ALOHA 关节位置/动作；
2. `AlohaFK.fk()` 用 forward kinematics 把前 6 个机械臂关节转换成末端三维位置；
3. 利用手眼标定得到的 extrinsics，把 robot-base 下的 EEF 位置转换到 camera frame；
4. 保存为 `obs/ee_pose` 和 `actions_xyz_act`。

Robot 仍保留原始关节动作 `actions_joints_act`，因为最终执行机器人需要 joint command；同时额外构造 camera-frame 下的 `actions_xyz_act`，作为能与 Human 手轨迹共享的公共监督。

#### 对齐后的结果

对于单臂样例：

```text
Human future hand pose: [100, 3] xyz in camera-related frame
Robot future EEF pose:  [100, 3] xyz in camera frame
```

这并不意味着人体手和机械夹爪的运动学完全相同，而是让二者至少在“相机看到的三维末端轨迹”这一层拥有同样的物理语义和维度。

### 5. Gap 三：采样率和动作速度不同

#### 问题

Human 约 30 Hz，Robot 约 50 Hz；人完成动作通常还比遥操作机器人快。若都简单取未来 100 个原始帧：

```text
Human 100 帧 ≈ 3.3 秒
Robot 100 帧 ≈ 2 秒
```

两条 chunk 表示的时间范围和任务进度会不一致。

#### 当前代码与论文的处理

论文说明：Robot 的 action chunk 覆盖约 4 秒，Human 覆盖约 1 秒，但最终都表示成 100 个未来 action query。这相当于在归一化的 chunk 索引中放慢 Human 轨迹，以贴近更慢的 Robot 操作。

Robot 转换代码：

```python
POINT_GAP = 2
FUTURE_POINTS_COUNT = 100
```

在 50 Hz 数据中，每隔 2 帧取一点，共取 100 点，覆盖约 4 秒。

Human 转换代码：

```python
HORIZON = 10
STEP = 3.0
```

在约 30 Hz 数据中，每隔 3 帧取一点，先构造约 1 秒的 10 点轨迹，再通过 `interpolate_arr(..., 100)` 插值成 100 点。

最终 HDF5 形状一致：

```text
Robot actions_xyz_act: [T_robot, 100, 3]
Human actions_xyz_act: [T_human, 100, 3]
```

重要的是：对齐的是模型所见的**序列长度和任务运动形态**，不是强迫两边原始采样率相同。第 `k` 个 query 表示 chunk 内的相对进度；它在原始 Human 和 Robot 记录中对应的真实时间间隔可以不同。

### 6. Gap 四：数值分布不同

#### 问题

即使两边都变成 camera-frame xyz，分布仍可能不同：

- 人和机器人工作空间不同；
- 手臂长度和运动范围不同；
- 人与遥操作机器人完成任务的路径不同；
- Aria 手部跟踪和机器人编码器的测量噪声不同。

你当前训练产生的统计量就能看到这种差异。Robot 的 EEF action 第一个时间位置大致为：

```text
mean ≈ [ 0.133, -0.024, 0.532]
std  ≈ [ 0.160,  0.072, 0.065]
```

Human 的 hand action 第一个时间位置大致为：

```text
mean ≈ [0.156, 0.235, 0.481]
std  ≈ [0.107, 0.075, 0.052]
```

尤其第二维均值差异很明显。如果共享 xyz head 直接拟合原始数值，它可以利用这种偏移轻易区分 domain，并学习两套互不相干的表示。

#### EgoMimic 的处理：各域独立 Z-score

对每个 domain 分别计算：

```text
x_normalized = (x - domain_mean) / domain_std
```

不是把 Human 和 Robot 所有数据混在一起算同一套均值方差，而是：

```text
Robot batch ──使用 ds1_norm_stats──> 近似零均值、单位方差
Human batch ──使用 ds2_norm_stats──> 近似零均值、单位方差
```

对应代码在 [`egomimic/pl_utils/pl_model.py`](../egomimic/pl_utils/pl_model.py) 的 `training_step()`：它从 Robot dataset 和 Human dataset 分别取得 normalization stats，并在各自 forward 前调用 `postprocess_batch_for_training()`。

验证或部署时，模型输出的是 normalized action，需要再用相应 domain 的 stats 反归一化：

```text
x_original = x_normalized × domain_std + domain_mean
```

这也是为什么 checkpoint 旁边保存 `ds1_norm_stats.pkl` 和 `ds2_norm_stats.pkl`，部署时不能只拿一个 ckpt 而丢掉统计量。

论文消融实验报告，移除 action normalization 会明显降低任务分数，说明这种看似简单的处理是跨域联合训练的关键，而非普通的数据清洗细节。

### 7. Gap 五：人手与机械臂外观不同

#### 问题

Human 图像里出现皮肤、手指和手臂；Robot 图像里出现机械连杆和夹爪。如果把原图直接送入共享视觉编码器，网络可能根据 embodiment 外观分流：

```text
看到皮肤 → 进入“Human 模式”
看到机械臂 → 进入“Robot 模式”
```

这会削弱 Human 数据对 Robot 表示的帮助。

#### EgoMimic 的处理：SAM mask + 红色方向线

Human 处理路径：

1. 用已跟踪的 hand pose 投影到图像，作为 SAM2 的 point prompt；
2. SAM2 分割手和手臂区域；
3. 将该区域设成黑色；
4. 根据 mask 范围叠加红色粗线，表达末端/手臂的大致方向；
5. 保存为 `front_img_1_masked` 和 `front_img_1_line`。

Robot 处理路径：

1. 从 `joint_positions` 通过 FK 得到机械臂关键点；
2. 用 extrinsics/intrinsics 投影到图像；
3. 作为 SAM2 prompt 分割机械臂；
4. 同样变黑并叠加红线；
5. 保存同名的 `front_img_1_line`。

相关源码是 [`egomimic/scripts/masking/utils.py`](../egomimic/scripts/masking/utils.py)。当前 medium 配置明确使用两边的 `front_img_1_line`，而不是普通 `front_img_1`。

效果不是让两张图像完全一样，而是：

- 减少最明显的 embodiment appearance cue；
- 保留场景、物体和交互位置；
- 用相似的抽象线条给两种 embodiment 提供方向信息。

### 8. 维度不一致到底怎么处理

这是源码中最关键的工程设计之一。

#### 8.1 当前单臂数据实际维度

| 信息           | Robot                      | Human              | 处理方式                                        |
| -------------- | --------------------------:| ------------------:| ----------------------------------------------- |
| front RGB      | `3×H×W`                    | `3×H×W`            | 共享第一个视觉 backbone                         |
| wrist RGB      | `3×H×W`                    | 不存在             | Robot 专用 backbone；Human forward 不传这个相机 |
| proprioception | joint position `7`         | hand `ee_pose` `3` | 两个不同 Linear 投影到相同 hidden dimension 512 |
| joint action   | `100×7`                    | 不存在             | Robot 专用 action head，只由 Robot loss 监督    |
| xyz action     | `100×3`                    | `100×3`            | 公共 hand/pose action head，两种数据都监督      |
| gripper        | joint/action 第 7 维中存在 | 没有直接等价标签   | 只属于 Robot joint head 的监督                  |

代码没有把 Human `ee_pose` 后面补四个 0 伪装成七维 robot joint，也没有删除 Robot wrist 图像来强求完全相同。

它采用的是：

```text
不同原始维度
      │
      ├── Robot proprio Linear: 7 → 512
      └── Human proprio Linear: 3 → 512
                                   │
                                   ▼
                         统一 hidden token 维度
```

动作侧也是：

```text
共享 Transformer hidden [B, 100, 512]
      │
      ├── Robot joint head: 512 → 7
      └── Human/pose head:  512 → 3
```

因此“对齐维度”发生在**learned embedding space** 中，不要求 raw tensor 的最后一维原本就一样。

#### 8.2 哪些能力 Human 无法直接监督

Human 数据没有：

- Robot wrist camera；
- 七维 joint configuration；
- 机械夹爪开合量；
- 机器人关节限制和动力学；
- 当前样例里也没有力/触觉或接触力标签。

所以 Human batch 不会直接给这些输出提供 target。它的作用是更新公共 front vision、共享 Transformer、共享 xyz action head，使模型从更多场景和物体中学习“看到什么、手应该往哪里运动”。Robot batch 再把共享表示落实到真正可执行的 joint/gripper action。

这也说明 Human 数据不是 Robot 数据的完全替代品：至少在该架构中，仍需要 Robot 示范连接 xyz 意图与具体机器人 joint control。

### 9. 联合网络的具体结构

相关代码在 [`egomimic/algo/egomimic.py`](../egomimic/algo/egomimic.py) 的 `EgoMimicModel` 和 `EgoMimic`。

#### Robot forward

```text
front_img_1_line ─> front ResNet ─┐
right_wrist_img  ─> wrist ResNet ─┼─> shared Transformer ─┬─> robot_action_head: 7D joint
joint_positions ─> robot state proj┘                       └─> hand_action_head: 3D xyz
```

训练 Robot batch 时，StyleEncoder 使用 Robot 的当前 joint state 和真实 joint action chunk 产生 VAE latent；Transformer 同时输出：

- `a_hat[0]`：未来 100×7 joint action；
- `a_hat[1]`：未来 100×3 xyz action。

Robot reconstruction loss 是两者之和：

```text
L_robot_recon = L1(pred_joint, true_joint)
                + L1(pred_xyz, true_xyz)
```

Robot 数据中的 `true_xyz` 不是人工另标，而是数据预处理阶段通过 FK 和 camera extrinsics 从 Robot 动作计算出来。

#### Human forward

```text
front_img_1_line ─> 同一个 front ResNet ─┐
ee_pose ─> human state projection ───────┼─> 同一个 Transformer ─> 同一个 3D xyz head
human xyz action ─> human action projection/StyleEncoder
```

Human 没有进入 wrist ResNet，也不调用 7D robot joint head。

Human reconstruction loss：

```text
L_human_recon = hand_lambda × L1(pred_xyz, true_human_xyz)
```

代码也用 `hand_lambda` 缩放 Human KL loss。

#### 共享和不共享的参数

| 参数部分                      | Human 更新 | Robot 更新 |
| ----------------------------- | ---------- | ---------- |
| front image ResNet            | 是         | 是         |
| wrist image ResNet            | 否         | 是         |
| Transformer encoder/decoder   | 是         | 是         |
| StyleEncoder 主体             | 是         | 是         |
| Human state/action projection | 是         | 否         |
| Robot state/action projection | 否         | 是         |
| 公共 3D xyz action head       | 是         | 是         |
| Robot 7D joint action head    | 否         | 是         |

论文所说的“只在末端用很少的专用层分开”，目的就是限制网络各自建立两套完全独立系统，迫使大量中间表示被共同优化。

### 10. 联合训练时一个 step 怎样执行

#### 10.1 双 DataLoader

[`egomimic/pl_utils/pl_data_utils.py`](../egomimic/pl_utils/pl_data_utils.py) 的 `DualDataModuleWrapper.train_dataloader()` 返回：

```python
return [robot_dataloader, human_dataloader]
```

PyTorch Lightning 对多个训练 DataLoader 使用组合加载。当前 medium 每个 epoch 只取 100 个 combined steps，而两边数据都足够长，所以每一步都会拿到：

```text
Robot batch: 4 samples
Human batch: 4 samples
```

这意味着当前数据混合比例按 batch 是 1:1，而不是按 HDF5 中两个 domain 的总样本数量成比例抽样。

#### 10.2 `training_step()`

[`egomimic/pl_utils/pl_model.py`](../egomimic/pl_utils/pl_model.py) 中的流程可以展开为：

```text
收到 [robot_batch, human_batch]
        │
        ├── robot_batch
        │     ├── ac_key = actions_joints_act
        │     ├── robot normalization stats
        │     ├── EgoMimic._forward_training(type=robot)
        │     └── 得到 robot loss dict
        │
        └── human_batch
              ├── ac_key = actions_xyz_act
              ├── human normalization stats
              ├── EgoMimic._forward_training(type=hand)
              └── 得到 human loss dict

对应 loss 分别 stack 后求平均
        │
        ▼
返回 total action_loss 给 Lightning
        │
        ▼
backward → AdamW.step → scheduler.step
```

数据集在 [`egomimic/utils/dataset.py`](../egomimic/utils/dataset.py) 给 Robot 样本添加 `type=0`、Human 样本添加 `type=1`。`EgoMimic._modality_check()` 根据这个值决定走哪个分支，并要求一个 batch 内不能混合两种 type。

#### 10.3 当前总 loss 的近似表达

忽略 padding mask 展开后：

```text
L_R = L1(robot joint prediction, robot joint target)
    + L1(robot xyz prediction, robot xyz target)
    + beta × KL_R

L_H = hand_lambda × L1(human xyz prediction, human xyz target)
    + beta × hand_lambda × KL_H

L_total = (L_R + L_H) / 2
```

当前配置：

```text
beta = kl_weight = 20
hand_lambda = 1.0
```

一般非预堆叠序列会通过 `pad_mask` 屏蔽运行时补齐的位置。但当前配置为 `prestacked_actions=true`，每个 HDF5 时刻已经包含完整的 `[100, D]` action chunk；Dataset 只取这一个预存 chunk，并把当前时刻的有效标记重复 100 次。Robot 数据制作时，越出 demo 尾部的未来索引已经被截到最后一帧，因此这些重复的末尾 action 仍参与 L1 loss，而不是被当前 `pad_mask` 排除。

### 11. 与只训练 Robot 或只训练 Human 有什么不同

#### 11.1 只训练 Robot：当前 ACT baseline

`act_medium.json` 只加载：

```text
Robot input  = front_img_1 + right_wrist_img + joint_positions
Robot target = actions_joints_act [100, 7]
```

普通 `ACT` 只有一个 action head，直接预测 7D joint chunk。它不会读取 Human 数据，也不要求 Robot 的辅助 xyz head。

优点：

- 数据语义最直接；
- 所有标签都与真实 Robot 控制完全一致；
- 流程简单，容易调试。

局限：

- Robot demo 收集昂贵、慢；
- 场景、物体和执行方式多样性受限；
- 视觉表示只从少量 Robot 数据学习。

#### 11.2 只训练 Human：`actHand.json` 所代表的路径

Human-only ACT 可以学习：

```text
Human front image + ee_pose → future hand xyz
```

它可以成为手部轨迹预测器，但没有学会 Robot joint/gripper action，因此不能把它的输出不经转换就发给当前 ALOHA 执行。

如果另做 inverse kinematics 或低层控制器，可以尝试把 xyz 转成 Robot action，但那是一个额外系统，并不是当前 Human-only 配置自动完成的。

#### 11.3 Human + Robot 联合训练：EgoMimic

联合训练同时获得：

- Human 数据的场景、物体和操作多样性；
- Robot 数据与真实可执行 joint action 的联系；
- 两边共同监督的 xyz 轨迹语义；
- 公共视觉/Transformer 表示；
- Robot 独有 wrist、joint、gripper 能力不被丢弃。

Human loss 更新共享层后，会改变 Robot forward 使用的同一组 front feature 和 Transformer 参数。因此即使 Human 从未提供七维 joint 标签，它仍可以**间接**改善 Robot joint prediction 所依赖的视觉与任务表示。

但这不是保证一定提升。若两域任务、视角、物体或动作语义差异过大，Human 梯度也可能干扰 Robot 学习，形成 negative transfer。EgoMimic 用硬件、mask、坐标、时间和 normalization 多层处理来降低这一风险。

### 12. 用当前 BowlPlace 数据走一遍具体样本

假设取 Robot `demo_0` 的时刻 `t=500`。

#### Robot 样本

HDF5 读取：

```text
obs/front_img_1_line[t]      → [480, 640, 3]
obs/right_wrist_img[t]       → [480, 640, 3]
obs/joint_positions[t]       → [7]
actions_joints_act[t]        → [100, 7]
actions_xyz_act[t]           → [100, 3]
type                         → 0
```

组成 batch size 4 后，经过 observation processing：

```text
front image  → [4, 3, 480, 640]
wrist image  → [4, 3, 480, 640]
qpos         → [4, 7]
joint target → [4, 100, 7]
xyz target   → [4, 100, 3]
```

模型产生两个预测并计算 joint + xyz loss。

#### Human 样本

同时可能取 Human `demo_17` 的某个时刻 `u`。它和 Robot `t=500` **不需要是相同任务阶段，也不是配对样本**：

```text
obs/front_img_1_line[u] → [480, 640, 3]
obs/ee_pose[u]          → [3]
actions_xyz_act[u]      → [100, 3]
type                    → 1
```

组成 batch size 4 后：

```text
front image → [4, 3, 480, 640]
hand pose   → [4, 3]
xyz target  → [4, 100, 3]
```

它使用 Human 自己的统计量归一化，经共享 front ResNet 和 Transformer，从公共 xyz head 得到预测并计算 Human loss。最后 Robot loss 与 Human loss 平均，一次更新所有相关参数。

### 13. 这种对齐仍然没有解决什么

理解方法的边界和理解方法本身同样重要。

1. **没有显式 Human-Robot 样本匹配。** 模型依靠共享任务规律和公共 xyz 监督自行学习对应关系。
2. **没有给 Human 补出真实 gripper 标签。** 抓取/松开只能主要从 Robot 数据或视觉共现中学习。
3. **当前公共 pose 主要是位置 xyz。** 手腕/夹爪完整朝向、手指形态、力和接触信息没有成为相同维度的公共动作监督。
4. **独立 Z-score 只对齐一阶和二阶统计。** 它不能保证复杂的多峰动作分布完全相同。
5. **SAM mask 可能失败。** 遮挡、快速运动或 prompt 不准会留下错误 mask；部署若也依赖 masking，还会引入额外故障点。
6. **Human 和 Robot 的真实动力学仍不同。** 同样的末端轨迹对 Robot 来说可能受关节限制、碰撞或速度限制影响。
7. **离线 MSE 不等于任务成功率。** 最终仍需闭环 rollout 检验误差积累、碰撞和接触操作。

所以 EgoMimic 不是“把人类视频自动变成完美 Robot action”的魔法转换器。它的核心思想是：找到尽可能多的公共结构，让便宜丰富的 Human 数据更新共享策略，同时保留少量但关键的 Robot 专用监督。

### 14. 将“对齐”浓缩成一张表

| Gap      | 具体问题                        | EgoMimic 的解决方法                      | 代码/数据体现                              |
| -------- | ------------------------------- | ---------------------------------------- | ------------------------------------------ |
| 视角     | 人眼第一视角 vs 机器人相机      | Robot 主传感器也采用类似 Aria 视角       | 两边都有 `front_img_1_line`                |
| 外观     | 人手 vs 机械臂                  | SAM2 mask + 红色方向线                   | `scripts/masking/utils.py`                 |
| 坐标     | Aria/device/world vs robot base | 都转换成当前 camera-related xyz          | Aria SLAM 变换、Robot FK + extrinsics      |
| 时间     | 30 Hz/快速 vs 50 Hz/较慢        | 不同时间 horizon，统一插值到 100 queries | Human 10→100，Robot gap=2 × 100            |
| 分布     | 工作空间均值/方差不同           | 每个 domain 独立 Z-score                 | `ds1_norm_stats.pkl`、`ds2_norm_stats.pkl` |
| 状态维度 | Human 3D、Robot 7D              | domain-specific Linear → 512D token      | human/robot state projection               |
| 动作维度 | Human 3D、Robot 7D              | 公共 xyz head + Robot joint head         | `EgoMimicModel` 双 head                    |
| 额外相机 | Human 无 wrist                  | Human 只走 front，Robot 走 front+wrist   | `camera_keys[:1]` vs `camera_keys`         |
| 数据量   | 两边 demo 数和长度不同          | 每 step 各采一个 batch，loss 平均        | `DualDataModuleWrapper` + `ModelWrapper`   |

### 17. 最后的核心认识

EgoMimic 的 Human-Robot 对齐不是单个技巧，而是一条完整链路：

```text
Human Aria / Robot sensors
        │
        ▼
相似第一视角 + 各自状态
        │
        ▼
坐标变换、时间重采样、SAM 外观处理
        │
        ▼
各 domain 独立归一化
        │
        ▼
Human: front + 3D hand pose/action
Robot: front/wrist + 7D joint + 3D EEF action
        │
        ▼
专用输入投影 → 公共 hidden dimension
        │
        ▼
共享 front vision + Transformer + xyz head
        │
        ├── Human xyz loss
        ├── Robot xyz loss
        └── Robot joint loss
        │
        ▼
一次联合反向传播，最终获得可输出 Robot joint action 的策略
```

它既没有粗暴地删除 Robot 独有信息，也没有伪造 Human 不存在的关节标签；它把“公共知识”和“具身专用能力”放在网络的不同部分学习。这就是当前代码中联合训练与单域训练最本质的区别。
